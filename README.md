# Dialogue Analyzer

Сервис для анализа переписок менеджеров с клиентами: автоматически находит проблемные места в диалогах (клиент не ответил, менеджер долго отвечал, возражение не отработано) и показывает их с привязкой к сообщениям, критичностью и сработавшим правилом. Набор правил настраивается без разработчика.

---

## Быстрый старт

Нужен только Docker. Одна команда поднимает базу, бэкенд, воркер очереди и фронтенд, применяет миграции и засеивает демо-данные:

```bash
docker compose -f docker-compose.dev.yaml up --build
```

Открывать — **http://localhost:5173**.

> **Прод:** `docker compose up --build` — nginx отдаёт собранный SPA и проксирует `/api` на php-fpm, приложение на **http://localhost:8000**. Для прод версии прокси не подходит, сделано под требование запуск одной командой.

---

## Ролевая система

В проекте реализовано простое ролевое разделение. Клиентов считаем что-то по типу экстранета, и что они создаются в системе, для связи с авторством сообщения.

| Логин | Роль | Пароль | Что видит |
|---|---|---|---|
| `admin@example.com` | админ | `password` | все диалоги + раздел «Правила» |
| `anna@example.com` | менеджер | `password` | только свои диалоги |
| `igor@example.com` | менеджер | `password` | только свои диалоги |

## Возможности

- Вход по ролям на сессионной аутентификации (Sanctum SPA, httpOnly-кука + CSRF).
- Список диалогов и просмотр переписки: сообщения с временем, итог (купил / не купил), пагинация, подгрузка старых сообщений по кнопке.
- Автоматический анализ диалога: для каждой находки — что произошло, критичность, какое правило.
- Управление правилами (админ): вкл/выкл, критичность, параметры — из интерфейса, без кода.
- Разграничение доступа: менеджер видит свои диалоги, админ — все.

## Архитектура

### Модульный монолит

Код разложен по доменным модулям (`app/Modules/*`), а не по техническим слоям — новую функциональность добавляешь внутри одного модуля.

```
app/Modules/
├── Shared/       конверт ответа, коды ошибок, глобальный обработчик исключений
├── Users/        пользователь, роли, middleware «только админ»
├── Auth/         вход/выход, текущий пользователь
├── Dialogues/    диалоги, сообщения, доступ (Policy)
├── Rules/        каталог правил: стратегии-логика, модель-настройки, реестр, админ-CRUD
└── Analysis/     исполнение: движок, очередь, результаты (события)
```

Зависимости направленные, без циклов:

```
Analysis ──▶ Rules ──▶ Dialogues
   └───────────────────▶ Dialogues
```

`Rules` (что за правила и как настроены — это админ) и `Analysis` (движок, очередь, результаты — это система) разделены: меняются по разным причинам.

### Правила: логика в коде, настройки в БД

- **Класс-стратегия** в `Rules/Strategies/` — логика детекта, реализует `AnalysisRule`; реестр находит по папке автоматически.
- **Строка в `rules`** — вкл/выкл, критичность, параметры (пороги, маркеры); правит админ из UI, применяется без деплоя.

**Почему такой формат.** ТЗ требует управлять правилами без изменения кода — значит часть правила должна лежать в БД. Вопрос — что именно. Рассматривал два «чистых» варианта и отклонили оба:

- **хранить логику правил в БД** (условия как данные, которые исполняются на лету) — **небезопасно**: интерпретация выражений из БД открывает инъекции и исполнение произвольного кода;
- **свой движок обработки правил** (DSL + парсер + интерпретатор условий) — **очень сложно**

Поэтому — **гибрид**: логика детекта в типобезопасном PHP-классе (тесты, ревью, вся мощь языка), а в БД только настройки (вкл/выкл, критичность, пороги, маркеры), которые правит админ из UI. Логику меняют редко и это работа программиста; настройки — часто и без разработчика.

**Сами параметры — в jsonb-колонке `config`, не отдельными полями.** У правил разный набор настроек (`min_messages`, `threshold_minutes`, список маркеров…). Варианты хранения в БД:

- **колонка под каждый параметр** — бесконечный рост схемы: миграция на каждое новое правило, плюс куча пустых полей у правил, которым этот параметр не нужен;
- **jsonb `config`** (выбран) — произвольная схема параметров без миграций; их смысл и типы знает сам класс-стратегия, он же читает `config` при анализе.

Новое правило = новый класс (реестр подхватит по папке), новая настройка = клик в админке. Стратегия + реестр — стандартный способ держать расширяемый набор алгоритмов.

Синхронизация — сидер `RuleSeeder`: новые стратегии заводит с дефолтами, удалённые из кода чистит, настроенные админом строки не трогает.

### Анализ (очередь)

```
сид / изменение правила → AnalyzeDialogueJob → воркер → DialogueAnalyzer
    → прогон включённых правил → analysis_events
```

В задачу кладётся `id` диалога (данные перечитываются свежими). Повтор идемпотентен: старые события удаляются и создаются заново. Изменение правила публикует событие `RuleUpdated`, `Analysis` его слушает и ставит переанализ — так `Rules` не зависит от `Analysis`.

### Формат ответов

```json
{ "success": true,  "data": { ... } }
{ "success": false, "error": "FORBIDDEN", "errorMessage": "Доступ запрещён." }
```

Контроллеры только бросают исключения — глобальный `ApiExceptionHandler` превращает их в конверт с нужным статусом (коды в `ErrorCode`-enum). Валидация через `FormRequest` → типизированный DTO в сервис.

### Авторизация

- Раздел «Правила» — middleware `admin` на роут-группе (не-админ → `403`).
- Доступ к диалогу, его сообщениям и событиям — `DialoguePolicy` : свои видит менеджер/клиент, все — админ. Список фильтруется запросом в сервисе (Policy проверяет объект, не коллекцию).

## Правила из коробки

| Правило | Критичность | Что ловит |
|---|---|---|
| Клиент перестал отвечать | высокая | последнее слово за менеджером — лид потеряли, нужен повторный контакт |
| Долгий ответ менеджера | средняя | ответ позже порога — медленная реакция роняет конверсию |
| Возможное возражение | средняя | маркер в реплике клиента («дорого», «подумаю») — возражение могли не отработать |
| Менеджер не поздоровался | низкая | нарушен стандарт приветствия |
| Монолог менеджера | низкая | несколько сообщений подряд без ответа клиента |

Пороги и маркеры лежат в настройках правила, правятся из админки.

## Добавить новое правило

1. Класс в `backend/app/Modules/Rules/Strategies/`, реализует `AnalysisRule` (`code`, `name`, `defaultSeverity`, `defaultConfig`, `analyze`).
2. Синхронизация: `php artisan db:seed --class=Database\\Seeders\\RuleSeeder` (или перезапуск контейнера — сид на старте).

Реестр подхватит стратегию по папке, в БД появится строка с дефолтами, правило доступно в админке. UI и ядро не трогаются.

## Dev и прод

**Dev** (`docker-compose.dev.yaml`): Vite с hot-reload на `5173` проксирует `/api`; Laravel через `artisan serve`, код примонтирован; Postgres проброшен на `5432` для IDE.

**Прод** (`docker-compose.yaml`): многоступенчатая сборка, nginx отдаёт статику SPA и проксирует `/api` на php-fpm; код зашит в образ; Postgres наружу не светится.

В обоих — отдельный воркер `queue:work` с `restart: unless-stopped`.
